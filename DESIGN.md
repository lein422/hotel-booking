# DESIGN.md

## 2.1. Архітектура програми

Програма побудована за багаторівневою архітектурою.

- Model – класи Guest, Room з похідними StandardRoom, FamilyRoom, Suite та Booking.
- Service – бізнес-логіка, перевірка бронювань і робота з файлами.
- Controller – обробка запитів інтерфейсу та запуск фонових задач.
- View – графічний інтерфейс на основі Tkinter.

Для зберігання даних використовується формат JSON.
XML застосовується для формування звітів про завантаженість номерів.

## 2.2. Основні алгоритми

### Перевірка конфліктів бронювання

Для кожного бронювання перевіряється номер кімнати та період проживання.

Два періоди перетинаються, якщо дата заїзду першого бронювання раніше дати виїзду другого, а дата заїзду другого раніше дати виїзду першого.

Якщо знайдено перетин, створення або редагування бронювання відхиляється.

Під час імпорту бронювання розкладаються по номерах кімнат. Кожен номер – окрема задача для ThreadPoolExecutor: задача сортує бронювання номера за датою заїзду і шукає перший перетин. Потоки лише читають дані, а результати збирає потік, що запустив пул, тому окреме блокування не потрібне. Дані сервісу під час імпорту захищені threading.Lock.

Однопотоковий режим перевіряє ті самі групи по черзі. Порівняння режимів – скрипт tools/benchmark.py.

### Пошук вільних номерів

Номер вільний на період, якщо жодне його бронювання не перетинається з датами заїзду і виїзду. Фільтр за типом і датами працює на вкладці «Номери».

### Формування XML-звіту

1. Отримання номерів, бронювань і звітного періоду.
2. Перевірка дат.
3. Підрахунок зайнятих ночей кожного номера.
4. Розрахунок відсотка завантаженості та доходу.
5. Формування XML-документа.
6. Збереження звіту у файл.

### Фонові операції

Імпорт, експорт JSON та формування XML виконуються в окремому потоці.

Результати передаються через чергу повідомлень.
Графічний інтерфейс перевіряє чергу кожні 100 мс за допомогою root.after().
